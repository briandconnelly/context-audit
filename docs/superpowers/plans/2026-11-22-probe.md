# Harness Probe (Phase 0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish, by running Claude Code against local fixtures, which of the harness behaviours the `context-audit` design depends on actually hold on the installed build.

**Architecture:** A dev-only `probe` package drives the real `claude` CLI inside a disposable profile with outbound network denied except loopback.
A local stub stands in for the model endpoint: it returns scripted tool calls and records every request the harness sends, which is the evidence of what reached the model.
A fake MCP server supplies marked content, a recording hook captures what each hook event receives, and a runner turns scenarios into `shown` / `not_shown` / `inconclusive` outcomes and a written report.

**Tech Stack:** Python 3.13+, standard library only at runtime, `uv`, `pytest`, `ruff`, `ty`; macOS `sandbox-exec`; Claude Code 2.1.330 as installed.

**Spec:** `docs/superpowers/specs/2026-11-22-third-party-context-audit-design.md` (sections Probe, Coverage status, Delivery, Evidence).

## Global Constraints

- Working directory is `~/projects/context-audit`; nothing is written to `~/projects/skills`.
- No real model session and no model quota: every `claude` run goes to the loopback stub, with synthetic credentials.
- If the harness cannot be routed to the stub, stop and ask the owner before using a real model session.
- Every `claude` run uses a disposable profile and has outbound network denied except loopback.
- Never run `claude mcp list` (it starts plugin servers) or any command that opens a real model session.
- The vendor behind the motivating incident is never named; fixtures use generic markers and placeholder names.
- Runtime code is standard library only; `pytest`, `ruff`, and `ty` are dev dependencies.
- `requires-python = ">=3.13"`; MIT license.
- Markdown uses one sentence per line.
- Commits follow conventional commits.
- Outcomes are exactly `shown`, `not_shown`, or `inconclusive`. A failed setup is `inconclusive`, never `not_shown`.
- Every claim is measured against a baseline run in which the claim could have failed.
- Hook output field names below come from a documentation summary and are unverified; Task 4 confirms them against the live reference before they are used.
- Deviation from the spec's Probe table: the gate claim is probed for accept, decline, dismiss, and retry only. Two gated tools and parallel gated calls are left to the slice 2 plan, and the report says so.

## Review Focus

1. Claude Code tries to reach another host at startup and waits when it is blocked: the runner must time out and report `inconclusive`, not hang.
2. Real credentials in the parent environment (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, a saved sign-in) leak into a run: the run environment is an allowlist and a test proves those variables are absent.
3. The harness sends a request the script does not expect (token counting, title generation, a second model): the stub answers with a harmless default, records it, and never crashes.
4. A marker shows up in the next request because the probe's own hook echoed it: hook-emitted markers are distinct from fixture markers, and checks name which one they look for.
5. Evidence left by an earlier run is read as this run's: every scenario gets a new, empty run directory, and the runner refuses a non-empty one.

Each has a test in the task that owns the code (Tasks 1, 1, 2, 6, 5).

### Task 2: The model endpoint stub

**Files:**
- Create: `probe/stub.py`
- Test: `tests/test_stub.py`

**Interfaces:**
- Produces: `ToolCall(name: str, input: dict, id: str)`, `Reply(text: str = "", tool_calls: tuple[ToolCall, ...] = ())`.
- Produces: `Stub(script: list[Reply], capture: Path)` as a context manager with `.url: str` (`http://127.0.0.1:<port>`) and `.requests() -> list[dict]`.
  Each captured record is `{"n": int, "path": str, "scripted": bool, "auth": str, "body": dict}`, appended to `capture` as JSON Lines.
  `auth` is `synthetic` when the `x-api-key` header equals `sk-ant-probe-synthetic`, `other-key` for any other key, `bearer` for an `Authorization: Bearer` header, and `none` otherwise.
  Header values are never stored; a real credential could arrive here if a saved sign-in overrides the synthetic key.

Behaviour the tests pin:

- A `POST /v1/messages` whose body has a non-empty `tools` list consumes the next `Reply` from the script and is recorded with `scripted: true`.
- Any other request (no tools, another path such as token counting) gets a harmless default and is recorded with `scripted: false`: a one-word text reply for `/v1/messages`, `{"input_tokens": 1}` for a path ending `count_tokens`, and `404` JSON otherwise.
- When the script is exhausted, a scripted request gets a text reply `done`.
- When the body has `"stream": true` the reply is server-sent events in the Messages streaming order: `message_start`, then per block `content_block_start`, `content_block_delta` (`text_delta`, or `input_json_delta` carrying the whole tool input as one JSON string), `content_block_stop`, then `message_delta` with `stop_reason` `tool_use` or `end_turn`, then `message_stop`.
  Otherwise the reply is one JSON message with the same content.

Outcome = Literal["shown", "not_shown", "inconclusive"]

@dataclass(frozen=True)
class HookSpec:
    event: str            # e.g. "PostToolUse"
    matcher: str | None   # e.g. "mcp__.*"
    mode: str             # record | message | replace | ask
    label: str

@dataclass(frozen=True)
class Scenario:
    name: str
    claim: str                       # the behaviour row from the spec's Probe table
    script: list[Reply]
    hooks: list[HookSpec]
    allowed_tools: tuple[str, ...] = ("mcp__probe__*",)
    check: Callable[[Evidence], tuple[Outcome, str]] = ...

@dataclass(frozen=True)
class Evidence:
    run_dir: Path
    completed: Completed
    requests: list[dict]             # from the stub
    hook_events: list[dict]          # from the recording hook
    calls: list[str]                 # tool names from the fake server's counter
    transcript: Path | None          # located via a hook event's transcript_path

def run_scenario(s: Scenario, run_dir: Path, *, timeout: float = 120) -> Result
# Result(name, claim, outcome, reason, run_dir)
```

- Produces: `ALL_SCENARIOS: list[Scenario]` in `probe/scenarios/__init__.py`, extended by later tasks.
- Produces: `uv run python -m probe [--only NAME ...] [--out DIR]`, where `--only` may be repeated; default `--out runs/<UTC timestamp>`.
- Produces: `probe.runner.CLAUDE_ARGV0 = "claude"`, the executable name, so tests can substitute a fake.

`run_scenario` writes, inside `run_dir`: a settings JSON registering each `HookSpec` as a `command` hook (`python3 -I <abs path>/record.py`, with `PROBE_HOOK_LOG`, `PROBE_HOOK_MODE`, and `PROBE_HOOK_LABEL` set in the command), and an MCP config with one stdio server named `probe`.

```

### Task 6: Result delivery, error content, metadata, and transcript scenarios

**Files:**
- Create: `probe/scenarios/delivery.py`, `probe/checks.py`
- Modify: `probe/scenarios/__init__.py`
- Test: `tests/test_checks.py`

**Interfaces:**
- Consumes: `Scenario`, `Evidence`, `HookSpec`, markers.
- Produces, in `probe/checks.py`:

```python
def hook_saw(ev: Evidence, event: str, marker: str, *, label: str | None = None) -> bool
def next_request_has(ev: Evidence, marker: str) -> bool      # any scripted request after the first
def any_hook_event_has(ev: Evidence, marker: str) -> list[str]   # event names whose input contains it
def transcript_has(ev: Evidence, tool_use_id: str, marker: str) -> bool
```

Every scenario's check first requires the baseline fact that the marker reached the model (`next_request_has`); if it did not, the outcome is `inconclusive`, because the claim could not have failed.

Scenarios (each registers a `record` hook on `PostToolUse` and `PostToolUseFailure` with matcher `mcp__.*`, and scripts one tool call then `Reply(text="done")`):

| Name | Tool call(s) | `shown` when |
| --- | --- | --- |
| `result-text` | `echo_text` | `PostToolUse` input contains `TEXT_RESULT` and `SIBLING` |
| `result-structured` | `echo_structured` | `PostToolUse` input contains `STRUCTURED_RESULT` |
| `result-split` | `echo_split` | input contains both `SPLIT_A` and `SPLIT_B` |
| `result-big` | `echo_big` | input contains both `BIG_HEAD` and `BIG_TAIL`; the reason records whether the next request contains both |
| `error-tool` | `fail_tool` | a hook event contains `TOOL_ERROR`; the reason names which event |
| `error-protocol` | `proto_error` | a hook event contains `PROTOCOL_ERROR`; the reason names which event |
| `parallel` | `echo_text` and `echo_split` in one reply | one hook record per call, each complete |
| `competing-hook` | `echo_text`, two record hooks labelled `a` and `b` | both labels saw `TEXT_RESULT` |
| `metadata` | `echo_text`, a record hook on every event name from the hook-fields notes | `shown` if any event input contains `INSTRUCTIONS`, `TOOL_DESCRIPTION`, or `PARAM_DESCRIPTION`; `not_shown` otherwise, with the list of events inspected in the reason |
| `transcript` | `echo_text` | the transcript file contains `TEXT_RESULT` in the entry for the scripted tool-use ID |
